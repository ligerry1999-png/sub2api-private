# 私有 image-jobs 持久队列运维说明

## 结论

`/v1/image-jobs/*` 把“接收任务”和“调用上游生图”分开：只要队列没有达到容量上限，服务端先持久化请求并返回 `202 + job_id`；后台再复用原有用户与账号并发槽位执行。

这意味着：

- 440 个合法请求可以先全部排队，不再因为“已有 4 张在生成”而把其余请求拒绝在外。
- 排队成功不等于 440 张同时生成。真实执行速度仍由 API Key 所属用户和生图账号中较小的并发值决定。
- 服务异常重启后，已持久化但未完成的任务可以恢复，不依赖客户端一直保持 HTTP 连接。

## 两层限制

1. 队列容量（允许先保存多少任务）：默认 2,000 个未完成任务、请求正文合计 5 GiB。只有达到其中一个上限时，新请求才返回 `429 queue is full`。
2. 执行并发（允许同时调用多少上游任务）：调度器工作线程上限默认 64，但它不会绕过原有 Redis 并发槽位。实际上游并发等于“用户并发、可用账号槽位、调度器上限”三者的最小值。

例如，生图账号允许 50，但 API Key 所属用户只允许 30，那么实际最多同时执行 30，其余任务继续等待，不会被当成最终失败。

## 安全与恢复

- 磁盘只保存 API Key 的数据库编号，不保存完整 Key。真正执行前会从数据库重新读取；Key 被禁用或删除后，旧任务不能继续冒用它。
- 提示词、上传图片和结果文件使用私有文件权限。
- 定时清理只删除超过保留期的 `success`、`failed` 和 `canceled` 任务；`pending`、`running` 与未知状态一律保留。
- 临时并发占满、暂时无可用账号、网络错误和部分 `5xx` 错误会延时重试；参数错误、认证失败等永久错误不会无限重试。

## 发布与回滚

发布前的顺序是：

1. 在 Redis 写入带过期时间的“暂停领取”标记。此时新请求仍可入队，但不启动新的上游生图。
2. 只等当前 `running` 任务结束，不等待所有 `pending` 任务清空。
3. 服务器只加载 GitHub Actions 预先构建的镜像，不在生产机器构建。
4. 新进程健康后自动恢复领取。

旧版镜像不认识新队列，因此回滚到旧版时，未完成任务会保留在磁盘和 Redis，但不会继续执行。处理方式是修复新版后再次向前发布，不要在旧版中手工删除队列文件。

这条队列采用“至少执行一次”的交付方式：也就是宁可在异常重启后重新尝试，也不静默丢任务。极端情况下，如果上游已经接收请求、但本机还没来得及保存结果就突然断电，任务可能被再次执行。每个任务都会携带固定的 `Idempotency-Key: image-job:<job_id>` 来降低重复概率，但上游是否完全支持防重复并不由中转站控制。因此正常发布会先暂停取出新任务并等待正在执行的任务结束，不能直接强杀进程。

批量任务优先使用 `result_delivery=file_url`，让结果以文件地址返回；默认 Base64 会让 JSON 结果和本机磁盘占用明显变大。当前版本仍保留两种格式兼容，对象存储可以作为后续独立改造，不与本次队列修复绑在一起。

## 验证边界

批量验收使用本地假执行器和模拟 Redis，覆盖 440 个任务的接收、取队、重试、取消和重启恢复。这类验收不得访问真实生图 URL，不产生图片，不消耗账号额度。
